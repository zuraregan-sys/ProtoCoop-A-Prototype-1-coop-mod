## Ghidra findings (2026-11-10)

Ghidra 12.1.4 (official zip, SHA-256 pinned) and capstone were used for the analysis. The DLL was imported into a Ghidra project and the key functions below were decompiled.

**Correction to the earlier audit:** `0x104A29E0` is **not** `CreateOnlineManager`. It allocates 800 bytes and runs the `SoundManager` constructor (`snd_*` registrations). The decomp's `protomain.cpp` label is wrong. Do not use it as the online entry point.

**Actual startup and session path:**

- `EngineInitialize` (`0x1085EFB0`) calls `FUN_108BF5E0` at `0x1085F47E`.
- `FUN_108BF5E0` initializes the online subsystem: copies desync settings, creates the engine `OnlineManager` (`0x9C` bytes) and the `OnlineSync` object (`0x144` bytes), registers `online_DeterminePlayerIndex`, and sets engine flags.
- `OLS::Get()` returns the OLS singleton; `OLSPeer` constructor `0x108E7E80` calls the session bootstrap `FUN_108BF1B0` with a host/client role derived from `OLS+0x7C+0x14`.
- `FUN_108BF1B0` is the real session bootstrap:
  - allocates `ChannelManager` (`0x7C` bytes) at `OnlineManager+0x70`;
  - allocates `ConsoleManagerPeer` (`0x8C` bytes) at `+0x74`;
  - opens two channels at `+0x94` and `+0x98` (`0x108C31D0` / `0x108C35A0`);
  - stores the current simulation driver at `+0x78` and installs the `OnlineManager` as the driver;
  - initializes `OnlineSync` with the channel and peer, then calls `StartSync(peer, ...)`;
  - creates `DesyncHunterOnline` unless `HardwareProfile` is set.
- `OnlineManager::Slot4` (`0x108BF780`) is the network pump: checks the channel, updates the clock, sends queued messages, receives from the channel, and dispatches messages to `OnlineSync`.
- `StartSync` (`0x10833380`) is called from `FUN_108BF1B0`; `UpdateSync` (`0x108336F0`) is called from `SimulationTick` (`0x10838BA0`).
- `CoOpBehaviour::Update` (`0x104DB8E0`) advances the three state objects and signals event 4; `OnMessage` (`0x104DB980`) handles message type 2 and type `0x30` ids 0..4 (respawn/pairing/death state), allocating the state objects on first use.
- `CoOpBehaviour` is `0x18` bytes; fields at `+0xC`, `+0x10`, `+0x14` are the three state pointers; `MetaBehaviourCreatorImpl<CoOpBehaviour>` allocates `0x18` and constructs it.

**Correction to transport naming:** the `NetSession` / `NetConnection` names in `gamelink.h` are guesses. The real objects are `ChannelManager` (`OnlineManager+0x70`) and `Channel` (the value returned by its `Open`). `ChannelManager::Open` creates `MultiTailQueue` and `Channel` objects. The seam is still real, but it is `ChannelManager`/`Channel`, and that layer is exactly what the decomp marks as not reconstructed.

## Engine co-op architecture (decomp reference, 2026-11-16)

- **The original online layer is deterministic lockstep plus state commands, not VFX replication.** `engine::SyncObject` / `SyncMessage` (`syncobject.cpp`, 8 bytes: factory, value, index) exchange press/release acks; only one factory is registered in the retail build (`SyncObjectFactoryDefault(2, 1, 1)` from `0x104DC532`), so it cannot be the player movement stream. `OnlineControllerManager` (`FUN_108C8BF0`, with `TimeSync` and `ConsoleManager`) drives controller/state synchronisation, and `OnlineSync`/`SyncCommands` (`FUN_108C7D00`, types 0/1/2 with a machine mask and callback) synchronises game-state requests. `CoOpBehaviour` only carries death/respawn/pairing state, and the online fight tracks carry world-cell streaming and pairing volumes. Effects, powers, trails and decals were therefore generated by each peer from the same simulation.
- **The real session bootstrap is `FUN_108BF1B0`** (called from the `OLSPeer` constructor `0x108E7E80` with role `OLS+0x7C+0x14 == 0`, `10`, `100`). It creates `ChannelManager` (`FUN_108C37B0`), `ConsoleManagerPeer` (`FUN_108FE2A0`), the two channels at `OnlineManager+0x94/+0x98`, the `OnlineControllerManager` at `+0x7C`, installs it as the simulation driver, calls `StartSync(peer, ...)` and creates the desync hunter. `FUN_108BF5E0` already creates the `OnlineManager` at `DAT_11318530` during `EngineInitialize`, even in single-player.
- **Engine bootstrap reached (2026-11-16):** with a fake OLS service at `[OLS+0xA0]`, `param_3=2` for the ChannelManager (0 made a zero-size allocation) and the HardwareProfile/desync-hunter path skipped, `FUN_108BF1B0` returns: it creates the real `ChannelManager`, `ConsoleManagerPeer`, channels kinds 0/1/2/3/4, the `OnlineControllerManager` and calls `StartSync` (`connection` at global `0x1130DC5C`). The game then runs with the `OnlineManager` as its simulation driver, but local input is frozen waiting for the peer.
- **Damage and destruction sync (`sync_damage=1`):** `engine::HealthBehaviour` keeps `health` at `+0xC` and `dead` at `+0x24`; `SetHealth` (`0x108480D0`) also runs `CheckDeath`. Both peers send `H1` packets with `{u16 index, u16 serial, float health}` for every nearby object with a `HealthBehaviour` (5 Hz, chunks of 100), and the receiver applies only a lower health, so concurrent damage converges. `CheckDeath` (`0x10848100`) is hooked to send an immediate health-0 event, which makes the peer destroy the object with its own explosion/debris instead of waiting for the next snapshot. `g_applyingHealth` stops the loop. Verified stable for 50 s; destruction itself still needs a human test. An already-diverged world only aligns after both peers load a fresh mission state.
- **World snapshot crash guard:** calling `SetPosition` on an object whose transform attribute (`+0x1C`) is not a valid engine object crashed the client at `0x107E08E9`. The receiver now validates the attribute (plausible pointer, vtable in `0x10000000..0x11400000`, finite translation) before moving an object; the `PhysicsBehaviour` filter was removed because NPCs do not expose it through the behaviour list. A 60 s run sent 125-196 objects per snapshot, applied 64 per packet and stayed up. Position only; orientation and animation are still local.
- **World snapshot scale:** the 20-object cap was replaced by up to 512 objects per peer, 80 m around the sender, sent at 5 Hz in packets of 64 entries. Each entry is 14 bytes: `u16 index, u16 serial, i16 x/y/z at 1/8 unit, i16 yaw`. A stable run reported 160-173 objects per snapshot (groups of NPCs/vehicles included) and the receiver applied 64 per packet with no crash. No animation state is carried; yaw is reconstructed from the transform basis and pitch/roll stay local.
- **World snapshot filters empty handle slots:** the first version forwarded the first 20 entries of the handle table, which are placeholder objects with serial 0 and a zero transform at the origin; the receiver happily applied those, so the NPCs never moved. The scan now requires a non-zero serial, a non-zero basis and a non-origin position, and both peers send their own 60 m neighbourhood (the host owns the overlap: client entries within 40 m of the host player are ignored). Verified: real handles (655, 776, 779...) cross, the client applies 20/20 and the host applies the client's far entries, no crash.
- **Host-authoritative world snapshot (`sync_world=1`):** the handle table at `g_engine+0x128348C` (entries of 8 bytes: object at +0, serial at +4) has the same indexes and serials in both processes after loading the same save. The host scans the first `0x1800` entries every 100 ms, keeps the objects within 60 m of its player (skipping the player and the puppet), and sends `W1` + up to 48 entries of `{u16 index, u16 serial, x, y, z}`. The client looks each handle up, verifies the serial, and applies the position with the engine's `SetPosition` (`0x7E08E0`). Verified: a stable two-instance run applied 20/20 objects per snapshot with no crash. Each entry now carries the 3x3 transform basis as well as the position, so the receiving object keeps the host orientation. Animation state is still not sent.
- **Raw channel bridging is not safe:** `Channel::Send` (`0x108C3F90`) / `Channel::Receive` (`0x108C4030`) can be mapped by channel kind (the pointers returned by `ChannelManager::Open` are the `self` of Send). Bridging the sync channel (kind 4) alone is stable; bridging the controller/state channels (kinds 0/1/2) crashes in `FUN_108C5440` (`0x108C54E3`) because those payloads carry process-local values (the 46-byte controller messages contain stack pointers), not a portable wire format. The serialization belongs to the dead OLS/Quazal peer; `Channel::Receive` only exposes the queue entry (type at +9, source mask at +4, size at +0x10, payload at +0xC), not a portable stream.
- **The next piece is the peer serialization/transport**, not more channel routing. Without the OLS service, `ConsoleManagerPeer` has no wire format; reviving it means implementing that protocol or replacing the controller/state sync with a portable one.
- **A bare `StartSync` is not enough:** starting it with the fake owner and bridging the 8-byte messages with their type over UDP produced no sends and no movement messages, because the game's input path is not driven by the single retail sync factory. The full bootstrap (or the part of it that installs `OnlineControllerManager` and the state/input path) has to run.
- **`ChannelManager`/`Channel` layout:** `ChannelManager` is 0x7C bytes (`Open` 0x108C2F?; channels are created with `FUN_108C31D0`), `Channel` carries a `MultiTailQueue`; `StartSync` opens the session connection with `Open(4, unknown, capacity)`. Our fake `Channel` already intercepts send/receive, which is the seam for a Steam-backed channel.
- **Plan:** revive the bootstrap with fake network objects, bridge the channels over the existing transport, then let both peers run the same mission. The detailed phases and verification criteria are in `ENGINE-COOP-ROADMAP.md`.

- Two gameplay clients now run with the plugin and proxy; saves were not modified. The client only loaded gameplay when its window was brought to the front during the menu sequence.
- **Remote avatar works (placeholder model):** the plugin hooks `GameObjectSpawner::Create` (`0x107F25C0`) and records which template made which object. When `GetPlayerObject(0)` appears in that record list, its template pointer is the player's own template, with no name lookup needed (the engine strips name text from data-loaded names: `Name::GetText` answers `?Name?`). The client spawns a second `GameObject` through the same `GameObjectSpawner::Create`, registers it (passing `flag = true` so `Slot3` allocates its master-table slot), and stores its handle in `gPlayerHandles[1]` (`0x1126E410`).
- A puppet created from the **player template** is invisible: it shares the player's `Pose*`/`choreo::Puppet*` attributes, so the player's own mesh animates instead (Alex raised his arms when we spawned one). A puppet created from an NPC template renders independently, so the remote avatar currently uses the mission's `Soldier` template (name hash `0x2C48D34E`, looked up among the mission's spawn records or, failing that, by walking every inventory and comparing `MetaObjectTemplate+0x10`).
- **Verified in game:** with the host teleported +6 in X (`test_move=1` in `coop.ini`), the client shows a second soldier standing at the host's exact coordinates while the local Alex stays at the original spot. The puppet position is refreshed every 2 frames from the decoded `P1` packet.

The puppet is now created from the **player's own template** again, with `Soldier`/`Brawler` only as fallbacks.
- Sharing the player's `choreo::Puppet*` drove the player's pose a second time (Alex raised his arms, then lay down). Clearing that one attribute on the puppet (`ClearAttributeByVtable`, vtable `0x10D9653C`) keeps the player's animation normal and the puppet still draws, static.
- **The puppet could damage players.** A full player object keeps the whole fight stack, so a body landing on the local player drained his health to almost zero. `SetBehavioursEnabled(puppet, false)` (`0x107E0960`) removes that: the puppet still renders (verified with two Alex models on screen) but no longer fights, and the health bar stays full while the puppet overlaps the player. Do **not** clear the `PhysicsObjectHandle` attributes instead: the behaviours still dereference them and the game crashes at `0x908118`.
- **The puppet keeps collision and hit behaviours (`puppet_combat=1`):** every game object carries a behaviour controller (found at `GameObject+0x30`; entries are `Behaviour*` with the owner at `+4`), and `RttiName` reads the MSVC decorated class name (the `TypeDescriptor` holds it inline at `+8`). Only the pose drivers stay off (`CharacterMotionBehaviour`, `MotionTreeBehaviour`, `MotionStateBehaviour`, `IKBehaviour`) so the streamed pose is not overwritten; `PhysicsBehaviour`, `TouchBehaviour`, `CollisionAction`, `HitReaction`, `FightVariables`, `Charge`, `GrabSelection`, `Grabbable`, `Targetable`, `LockOnTargeting`, `ThreatReceiver`, `SensesInfo`, `PoisonReaction`, `PowerWheel` and `Tendril` stay on. Damage is neutralised with the engine's own `go_SetDamageScale(puppet, 0)` and `go_SetDamageable(puppet, false)`, called once the Lua state exists, so the players collide and hit each other without killing each other. Verified: 4 of 38 behaviours disabled, no crash, the puppet keeps walking normally. `puppet_combat=0` restores the purely visual avatar.
- The puppet now spawns on the ground next to the local player instead of at the origin, so it no longer falls and triggers the landing blast that threw and hurt the player.
- Driver cloning must not release the shared drivers: `Puppet::RemoveAll` frees objects the player's puppet still uses (crash at `0x6E77B7`). Clearing `mDriverCount` (`+0x190`) and rebuilding with `CopyDriverFrom` avoids the release.
- `puppet_static=1` in `coop.ini` falls back to the older static variant (clears the choreo puppet and disables behaviours).
- **Placement when both clients load the same save:** the two players start on top of each other, so the puppet is moved 1.5 units to the player's right and 1.5 behind (`x-1.5, z-1.5`) whenever the remote position is within 1 m of the local one. That side of this rooftop is solid, so it stays in view instead of hanging over the drop.
- **Query the player matrix once per frame.** Calling `Attribute<Matrix>::GetMatrix` twice per `UpdateSync` crashed the game with a `movaps` fault inside `HookUpdateSync`; one call per frame was stable at the time. The matrix is stored inline after the attribute's vtable, so `ReadInlineMatrix` now reads it directly and the virtual call is gone.
- **Root cause of the intermittent `movaps` crashes:** the engine calls `UpdateSync` with a stack that is not 16-byte aligned, and clang emitted 16-byte aligned SSE spills (`movaps %xmm, 0x10(%esp)`) inside `HookUpdateSync`, which fault on misaligned addresses. `-mstackrealign` and `force_align_arg_pointer` did not stop it; building `diagnostic.cpp` with `-mno-sse -mno-sse2 -mfpmath=387` does (only an aligned data load remains). Two-instance runs are stable again.
- **The engine's sync session must not be started:** `StartFakeSession` (fake `SyncOwner` + `NetSystem`) makes the engine own the player object, and local movement stops working - WASD and the left stick do nothing while powers and Escape still work. The transport now runs on our own UDP socket, ticked from a `ControllerSystem::Update` hook (`0x10643A20`) once per frame; `fake_session=1` stays only as a legacy option. Movement works again with the tick in place.
- **Test save:** a 100 % "STORY MODE COMPLETE +" save (HARD) was used as `slot-D`, with the real saves backed up beforehand. `CONTINUE` opens the slot list with slot 04 selected, so the menu automation loads it. The full power wheel is available for tests.

The plugin's `XInput` proxy can hold combos as a single button mask (`0x4000|0x8000`).
- **Power animations sync** through the pose stream (a Y power on the host shows the puppet performing the same animation); the power's visual effects (projectiles, shockwaves, tendrils) are replicated separately, see below.
- **Devastators replay their motion branch on the puppet:** the three devastators animate the player and spawn their cage/spikes/beam from the attack's own tracks (drawables), not from `EffectManager::StartEffect`. The active track path comes from the `DevastatorUsedMessage` (`0x14/0x21`, read through the `MotionTreeBehaviour` sequencer at `+0x18` with `GetTrackPath` `0x105A46C0`); the plugin sends it in an `A4` packet and the receiver calls `PlayMotionBranch` (`0x10868540`) on the puppet, enabling its pose drivers for the 4 s replay and pausing the host pose stream. An echo guard stops the puppet's own used message from being sent back. Verified in both directions with the real combos: the host sees the guest's tendrils/spikes/beam on the guest puppet and the guest sees the host's on the host puppet.
- **Attached effects without a part fall back to the puppet:** some effects (devastator bursts) carry a zero part name or a part the puppet only has while its own action runs; the old code dropped them (`part=0 → dropped`). They are now replayed as world effects at the sender's transform (`target = 0xFFFF`, empty part) so the visual is not lost; effects whose part resolves still attach to the bone.
- **The engine counts players explicitly:** `GetPlayerObject(i)` (`0x0099560`) validates the index against a count at `[0x11283290]+0x14` and reads the handle from `engine+0x126E40C + i*4` (then resolves it in the master object table). Single player keeps the count at 1, so even though this mod writes the puppet's handle at index 1, every engine system that loops players (AI targeting, ambient director, alerts) ignores it. `players_count=1` raises the count to 2 while the puppet exists (`players_count` in `coop.ini`); verified: both avatars render, HUD unchanged, no crash. The enemy-targeting part needs a combat check (host window: does an enemy attack the second avatar?).
- **Ambient spawn replication is half working:** the host records every object created by a spawner (`SpawnRecord`), sends the nearest ones around **both** players (`S3` snapshots, 32 entries per packet, every 500 ms) and the client learns those template hashes. Two blockers: (a) the client cannot create them because `FindContentObjectByHash` returns null for templates it has not loaded yet (the content is streamed/loaded per area), and (b) suppressing the client's own spawns by returning null from `GameObjectSpawner::Create` crashes the caller (`SendMessage` on the null object, `0x107E0827`), so the suppression is off by default (`spawn_suppress=0`). A safe director needs either a spawn-decision hook (spawner behaviour, before the create call) or the `DestroySpawnerSpawn` message for post-create removal.
- **Devastators: fight items, not effects:** the names `DevastatorTendril`, `DevastatorGroundSpike`, `DevastatorExplosion`, `TendrilDevastator` etc. are fight items, not drawable archetypes (`FindDrawableArchetype` returns 0 for all), which is why effect replication alone cannot draw them. The branch replay above is the path that works (the engine also exposes `go_PlayMotionBranchByPath`, `0x86C3A1` / factory `0x1086A9C0`).
- **The receiving camera stays under the player's control during a devastator replay:** the branch carries several camera tracks that act on the local player's camera, not on the puppet. On the firing process they are the intended cinematic; on the receiver they would steal the camera. While `g_puppetDevastatorUntil` is set the plugin returns false from the camera actions' start methods: `DramaticCameraAction::Slot5` (`0x10359A40`), `engine::CameraAnimationAction::Slot5` (`0x108F25A0`), `CameraClipPlaneAction::Slot5` (`0x108F2220`), `CameraResetAction::Slot5` (`0x10359080`), `PunchinCameraAction::Slot5` (`0x1035A390`), `CameraTypeSelectAction::Slot5` (`0x10358B20`), `CameraAvatarSelectAction::Slot5` (`0x10358940`), `ScriptedCameraAction::Slot5` (`0x1035A810`), `CameraHintAction::Slot7` (`0x10358DE0`) and `BlockFramerCamAction::Slot5` (`0x10359EC0`), plus the lower-level `DramaticCamera::Play` (`0x1084F7C0`) and `CameraManager::StartScriptedCamera` (`0x1032F9D0`). The normal chase camera keeps running, so the receiver can still look around; the firing player gets the whole cinematic. Different devastators use different tracks (the tests caught `PunchinCamera`, `DramaticCamera` and `CameraHint`), so the full set matters. Verified in both directions with the proxy's scripted right stick (`COOP_CAMERA_TEST=1`): the watching player's view kept rotating while the tendrils/spikes/beam played on the puppet, and without stick input the view stayed still.
- **Devastators cannot hurt the other player:** for the replay window the receiving local player gets damage scale 0 (`SetDamageScale`, `0x14/5`) and `SetUndamageable` (`0x14/7`) and is made untargetable (`SetTargetableTargetMessage`, `0x3B/5`) so the tendril grab cannot pull them; all are restored after 4 s. Verified numerically: the receiver's health stayed 1000 of 2700 through all three devastators.
- **Claws heavy attack (groundspike) is a separate ordinary fight branch:** holding heavy attack with Claws plays `//0x42d23566d0b706b3/.../0xdac11791eb45744e/0xfaa7614558fe7b51` (variants add `0x00684d3a156885ff`, `0x1e8b84af662f7d91` or `0x2eb6c0fbac2c6d60`). It is not a devastator and does not go through the input's `PlayMotionBranch`, so the plugin polls the local player's `MotionTreeBehaviour` sequencer (`GetTrackPath`, `0x105A46C0`) for the final track `0xfaa7614558fe7b51` and sends an `A5` packet with the full path, the player matrix and the camera view matrix. On receipt the puppet gets the sender's matrix, `Director::GetCameraMatrix` (`0x107DE6B0`) answers with the sender's camera for 1.2 s (the auto-target/shard spawn then aims at the same point), the puppet's pose behaviours are enabled so the branch's spawn tracks run, and the pose stream is kept running so the attack animation still plays. `PlayMotionBranch` (`0x10868540`) replays the path; the 4 s window reuses the devastator camera/damage guards. Verified in the street: spikes and ground cracks appear on the puppet in the same direction as the caster, with the full animation, and the caster's own view stays normal. - **Power effects sync (world effects):** the engine starts a power's effect through `engine::EffectAction::Slot5` (`0x108076B0`), whose target handle sits at `+0x40`. Only effects whose action targets the **local player** are forwarded, so the ambient city war (NPC/tank actions) never crosses. On receipt the archetype is resolved by **hash** in the local inventories (`DynamicCaster<DrawableArchetype>`, vtable `0x10D97DC4`, name via `0x108258B0`) and `StartEffect` (`0x1081E6B0`) is called with that **local name**. Verified with the Groundspike devastator (X+Y): the fire/spike effects appear on the peer.
- **Effect replication pitfalls:** never send the sender's `EffectSetup` wholesale. The store drawable (`+0x98`), the `useStore` flag (`+0x70`) and the attach part name (`+0x40`) are process-local; copying them made `StartEffect` abort. Replication uses local defaults plus only the world transform.
- **Attached effects are anchored by part name:** `EffectSetup + 0x40` is an 8-byte `core::Name` (64-bit hash). Copying it without validation crashed at `0x106E77B7`, because the engine indexes `lookup->matrices[part]` and `FindPart` can return an out-of-range value when the part is unknown. The receiver now resolves the name on the puppet's part lookup (`GetAttributeValue(puppet, 0x10E80688)`, `PartLookup::FindPart` at RVA `0x006DD6D0`), checks the index and only then copies the name; otherwise the effect stays on the puppet's root. Verified: the devastator tendrils now appear on the remote puppet's arm (not at its feet).
- **Re-forwarding guard:** `StartEffect` also fires when the receiver creates a replicated effect. `g_creatingRemoteEffect` stops those from being sent back to the peer (otherwise the two instances loop effects).
- **Transformations are synced from state, not from input:** the player's `TransformationBehaviour +0x10` holds a table of slots, 0x28 bytes each: slot name at `+0x00`, the desired `TransformationDescription*` at `+0x08`, the active description at `+0x0C` and the active flag at `+0x1C`. A `TransformationDescription` stores its own name at `+0x08` (portable 64-bit hash). The plugin snapshots this table ~10 Hz, sends only slot names/descriptions/active flags in an `S1` packet and starts the corresponding slot on the puppet with `StartTransformationMessage` (type `0x1E` id `4`). Because it observes the resulting state, it works for D-pad, the LB wheel, keyboard/quick keys, a generic pad or a mod - no input message is required. The latest snapshot is cached and replayed when the puppet respawns or the mission reloads. The puppet's `TransformationBehaviour` must stay enabled (its combat behaviours are off, so it only changes its own mesh).
- **Do not copy transformation pointers or send a desired description:** writing the slot's `+0x08/+0x0C` pointers or sending `SetDesiredTransformationMessage` with a description object from the other process makes the engine rebuild the pose and crash in `PoseData::SetRestPose` (`0x10708...`). This was solved by the name-based Lua path above (`go_SetDesiredTransformation`), which resolves the description locally.
- **Power wheel:** the state snapshot is paused while the local `PowerWheelBehaviour` is open (flag at `+0xC`). Reading or applying the transformation state during the wheel crashed the client (wild call); after the wheel closes the snapshot resumes and the selected power is applied. Verified: the host selects the blade in the LB wheel and the client's puppet shows the blade arms. This path is input-agnostic (the state is observed, not the input message).
- **Blade duplicates the arms on the puppet:** even with `bodyTemplate == 0`, `overrideLeftArmTemplate == 0` and `leftArmNeeded != 0`, Blades (`hudPower == 2`) add the blade templates on top of the puppet's normal arms. The receiver now applies only Claws (`hudPower == 1`); Blade/WhipFist/Armour/Shield/MuscleMass are skipped. The forced replay no longer re-sends `Start` for an unchanged applied slot, and the applied-slot cache is cleared when the puppet/player changes, so a transformation cannot be started twice.
- **The power is a model swap, not an arm attachment:** equipping a power changes the *character model*. `RenderBehaviour` keeps the drawable archetype `core::Name` at `+0x18` (source at `+0x2C`) and it changes on equip (default `93E14DA98B70B317`, Claws `A5E3C47B03550ECC`, Blade `45FE9B2D208F56C7`). `TransformationDescription +0x18` holds the same name hash (`hudPower` at `+0x64`). The local player's model swaps because the game loads the new archetype; the puppet kept the default model and that is why `StartTransformationMessage` produced four arms (normal arms + the power's arm mesh).
- **Model sync (`sync_model=1`):** the plugin sends the local `RenderBehaviour` model name (`M2` packet, 8 bytes: hash + process-local index; only the hash is comparable). The receiver looks the archetype up by hash in the content inventories and, when it is loaded, instances it with `render::Drawable::CreateInstance` and publishes it on the puppet's `RenderBehaviour` exactly like the engine's drawable message does: `SetDrawable` (`0x10862C30`) + `SetPose(render::Drawable::CreatePoseInstance)` (`0x107E8820`, `0x10862600`). Do **not** call `RenderBehaviour::SetSource` (`0x10862D60`): it crashes in `DrawableArchetype::CreatePoseInstance` (`0x10825963`) because the pure3d drawable belongs to the render thread. `CreateInstance` returns its result through a hidden pointer argument (sret), not EAX.
- **Power models load on equip and are released on unequip:** the body model of a power is not part of the map's content; the game loads it when the power is equipped. Sending `SetDesiredTransformationMessage` (ctor `0x101215B0`) with the weapons slot and the power's description name (`description+0x08`), followed by `StartTransformationMessage`, loads it synchronously (verified on hud 1-5). Toggling each power off again after loading corrupts the engine state: the fourth cycle faults at `0x10082907` in the transformation/drawable handler. `PreloadTick` therefore switches forward through the five arm powers and stops only once at the end, and keeps a reference on each archetype (`content::LoadObject::AddRef` `0x105FE740`) because the content system releases the model when the power is switched away. Verified: all five report `loaded=1` in both processes. The preload runs on the **local player** (the game swaps its model cleanly; the puppet kept a second set of arm meshes) and writes the slot's saved `desired` pointer back afterwards, so the player's own power selection is not left pointing at the last preloaded power.
- **The WhipFist model is the arm, not a body variant:** its description points at the drawable `5E358819`, which carries the whip arm and binds badly to the streamed pose (the whole puppet stretches). Its visible part is the tendril, a motion trail that is not replicated yet, so the model sync now skips that hash and keeps the puppet's current model.
- **Stale archetype cache broke every later model swap:** `FindDrawableArchetype` cached archetypes by hash and returned them unchecked, so after the content churn of a Whip equip the cached pointers were free memory and every later swap failed silently (no lookup error). The cache now validates the object's class before using it and drops stale entries. (Found through the model logs: `model recv` with no following `model apply`.)
- **The lookup must be incremental:** a full inventory walk is hundreds of thousands of `dynamic_cast`s and blocked the game for tens of seconds. `ModelArchetype` scans ~4000 objects per call (10 Hz) and stops at the first name match, so the model applies about one second after it is requested.
- **A swapped model needs `Drawable::SetPose` too:** after `SetDrawable`, the render behaviour only publishes the new pose in the object's attribute; the new drawable keeps its own pose, so every streamed joint was ignored and the puppet's body stayed frozen (only its own animation showed). `ApplyModel` now calls `render::Drawable::SetPose(handle, pose)` (`0x107EDA80`) so the renderer reads the same pose object the stream writes. Verified with a diagnostic twist of every joint: with the swap but without that call the mesh does not move, with the call it deforms immediately.
- **Model loading limit:** a game process only loads the archetypes its *own* player uses, so the receiver cannot swap to a power model it has never equipped (`model: <hash> not loaded here`). The model swap therefore renders the power only after that side has used the same power at least once. Preloading the power models is the open task.
- **Transformation `Start` replication is off by default (`transform_start=0`):** with the model swap in place, starting the transformation on the puppet only adds the extra arm mesh. Set `transform_start=1` to restore the old behaviour for debugging.
- **Slow motion disabled by default:** `no_slow_motion=1` installs a detour on `SlowMotionManager::Request` (`0x102A68E0`) and forces the request's simulation rate to 1.0, removing the impact/camera slow motion. Set `no_slow_motion=0` in `coop.ini` to restore it.
- **Transformations are filtered by `hudPower`:** `TransformationDescription` has a `hudPower` enum at `+0x64` (Claws=1, Blades=2, HammerFist=3, WhipFist=4, MuscleMass=5, Armour=6, Shield=8, ...). Applying WhipFist (`hud=4`) corrupted the pose (`PoseData::SetRestPose`, `0x107087FA`) and added a second set of arms; the crash then appeared on the other player in `pure3d::Scene::Add` (`0x107124DC`). The receiver now starts only Claws (`hud=1`) with `bodyTemplate == 0`, `overrideLeftArmTemplate == 0` and `leftArmNeeded != 0`. Deactivation only toggles slots that were actually applied; skipped slots never receive a Start on equip **or** unequip. Blade (`hud=2`) also duplicated the arms and is skipped. `transformationTemplate` (`+0xBC`) and `defaultLeftArmTemplate` (`+0xD8`) are shared `content::MetaObjectTemplate` objects between the player and the puppet; hiding the normal parts or cloning those templates is still pending.
- **Whip is an effect, not an arm mesh:** the whip power animates the arm but its visible tendril is a motion trail/span effect, not a `TransformationDescription` body/arm template. It is not replicated yet; `MotionTrailAction`/`CreateSpanEffectNamed` are the next hooks.
- **Disguise is a separate subsystem:** the LEFT quick slot in the 100 % save is the military disguise (soldier), not an arm power. It goes through `proto::DisguiseMessage`/`DisguiseChangedMessage`, not the transformation slots, and is **not replicated yet**.
- **Local transformation leak is cleaned:** the puppet shares the local player's transformation template, so a local transformation also appears on the avatar of the peer. After the local animation settles (~2.5 s) the plugin compares the local player's active slots with the peer's cached state, starts the leaked local-only slots on the puppet to toggle them off, and then reapplies the peer's active slots. Verified: while the client equips the whip, the host sees the whip on the client's puppet and the client sees the host's puppet normal; the client no longer sees its own whip on the host's avatar.
- **Whip-equip crash:** the crash at `0x1061A41B` is a copy to a null destination (`mov [esi+0x10], eax` inside the function at `0x1061A410`). A detour drops the copy when the destination is null and logs `copy: null destination` instead of writing through it. Tested with the host-first and client-first whip-equip orders, and with the power wheel, without crashes.
- **Do not disable the puppet's RenderBehaviour/TransformationBehaviour at runtime:** removing/re-adding its drawable corrupts the scene's drawable list and crashes in `pure3d::Scene::Add` (`0x107124DC`). That approach was removed; the null-copy detour is the crash guard. The state send/apply pause after a local start and the body/left-template skip remain.
- **Attached effects now replicate (`sync_attached=1` by default):** effects attached to the player (charge-jump tendrils, armour glows) go to the puppet; the part name is resolved on the puppet's pose and unknown parts fall back to its root. The earlier crash came from the receiver creating every copy the sender's action starts (up to 60 per second), which also made looping effects restart forever. Each effect (name + target + part) is now forwarded only when it reappears after a 3 s pause, so a tracked effect is created once and a new charge starts a new copy. World effects started by the state machines within 3 m of the player (landing dust, wall-run traces) are forwarded too; the broader capture is limited to `target == 0xFFFF` because forwarding attached effects from every code path reproduced the restart loop.
- **Effect stops are replicated:** the action that starts an effect also stops it, but the copy on the puppet had no action behind it, so looping effects (the charge sweep) never ended. Each replicated effect's `StartEffect` id is stored; when the local starts stop arriving for 500 ms, an `E2` packet names the effect and the receiver removes its own copies through the manager (`EffectManager::FindEffect` `0x0081B3F0` with the name-table node, then the remove routine `0x0081D790`; passing the node is required, a null one writes through `0x4`). Stopping by name alone (`0x0081E260`) is unsafe: it also kills the local player's own effect with that name.
- **Decals are not replicated yet:** the decal action (`DecalAction::Slot5`, RVA `0x00B0CB0`, and the HitEffectManager variant at `0x04FBAD0`) and the `AddDecalMessage` (type 61, delivered through `GameObject::ReceiveMessage` at `0x107E0810`) were mapped, but hooking the slot crashed both instances during the puppet spawn (`MH_CreateHook` on the message receiver had already been installed as `GameObject::SendMessage`; the slot hook itself was the crash). The message layout is: name pointer at `+0x0C`, position/normal/tangent pointers at `+0x10/+0x14/+0x18`, four floats at `+0x1C..+0x28`; the DecalBehaviour handler resolves the name through the effect manager and turns unknown names into `-1`. Reproducing a decal means rebuilding that message and delivering it to the puppet, but the hook has to be redone carefully (the raw slot hook is unsafe).
- **Motion trail WIP:** `SendMotionTrail`/`SpawnRemoteMotionTrail` and the `M1` packet are implemented (MotionTrailTrack fields: joints/offsets/shader/shrink/times), but installing the `MotionTrailAction::Slot5` hook at `0x10805D30` crashed both instances at startup (`0x10615FEB`); the install is disabled. Do not re-enable it without investigating the hook/trampoline; the packet path is not the cause.
- **Fast boot:** `run-coop.ps1` writes `args.txt` with the engine options `SkipMovies`, `NoMovie`, `NoFELoadingPrompt`, `NoAutoSave`, `NoSleepOnLostFocus` (plus `windowed`) and the proxy menu timings were cut to ~21 s; the save is playable in ~30 s instead of ~95 s. The frontend still appears briefly (the remaining time is the game's own load); a fully direct load would need Lua injection (`sgm_LoadGame`).
- **Capture diagnostics:** `tools/capture.ps1` grabs both windows on the same tick and labels each half (`0 HOST` / `1 CLIENT`); `contact.ps1` switches to two columns for these 1920-wide frames. `frames.csv` stores `GetTickCount` per frame and every log line starts with `t=<tick>`, so a frame can be matched to an effect send/receive. Schedule captures from each process's `StartTime`, not from the moment `run-coop.ps1` returns (it blocks while the game boots).
- **`dynamic_cast` on inventory objects** throws `std::__non_rtti_object` (and terminates the process) for objects without valid RTTI; validate the vtable range and the RTTI locator before every cast in the inventory scans. This was the cause of the "Runtime Error!" aborts when an effect arrived.
- **Per-mission state:** a new player object (respawn or loading another mission) invalidates the cached template, puppet, pose and rotation. `ResetCoopState` clears those but **keeps the spawn records**, which are how the player's template is found again.
- **Diagnostics:** `SetUnhandledExceptionFilter` logs the exception code and, for MSVC C++ exceptions (`0xE06D7363`), the thrown type name; `_set_invalid_parameter_handler` (MSVCR80) turns CRT aborts into logged no-ops; a watchdog thread logs `watchdog: stalled at phase N` when the frame stops.
- **The avatar also needs the object rotation:** the pose only carries joint transforms, not the character's facing. A 52-byte `R1` packet with the player's 3x3 basis is sent at ~20 Hz and written into the puppet's transform matrix each frame, so the remote avatar turns the same way the player does.
- **Animation is streamed as a pose and pushed into the drawable:** the character's `Attribute<Pose*>` (`0x10E80688`) points to a `pure3d::Pose` whose `PoseData` starts at `+0x10` (skeleton `+0x10`, joint count `+0x14` = 67 for Alex, rotations `+0x18`, translations `+0x1C`, matrices at `+0x20/+0x24/+0x28`, `spaces` `+0x3C`). Both roles send 67 quaternion+translation pairs (2148 bytes) at ~30 Hz. On receipt the plugin stores them and, **after** `RenderBehaviour::Update` (`0x108627B0`) copies the object pose to the drawable, writes the stored joints into the object pose, marks it dirty (`pose+0x40 |= 3`), calls `Pose::Update` (`0x106DD6E0`) and `Drawable::CopyPoseStateFrom` (`0x107E8740`) on `RenderBehaviour+0x14`. That last step is what makes the drawable actually draw the streamed pose (writing the object pose alone left the drawable in its rest pose, i.e. T-pose). The receiver nlerps the quaternions and lerps the translations toward the newest packet each render frame so the 30 Hz stream looks like the frame rate.
- **Smoothing:** transforms are sent every 6 ticks (~7 Hz) and the puppet lerps 25 % of the remaining gap per frame (snapping over 8 m), so it no longer jumps between packets.
- Position packets now use 1/8 units (range `+-4096`) instead of 1/32: the old scale clipped every coordinate past `+-1024` (the mission area sits around `z = 1215`, so the client placed the puppet at `1024`).
- `GetPlayerObject(1)` still returns null: it checks `InputSystem::sInstance+0x14` (the player count), which is 1. The handle is stored and resolves through the master table, but the engine's player-slot helpers refuse index 1 until that count changes.
- Name hashing is understood: `core::Name` is `{ u32 hash, u32 index }`, `hash = ((hash * 0x1003f) ^ sign_extended_char)` per byte. `"transform"` -> `0xBE42C46C` and `"meta object template"` -> `0x2E53EFD6` match the globals, so offline name matching works.

- **Powers are applied through the game's own Lua API:** the engine's script manager is the singleton at `gScriptManager` `0x11284254`, and the `lua_State*` is `manager+0x0C`. `manager->IsVariableDefined`/`PushGlobalFunction` confirm the stock helpers; the plugin reads the state directly and calls `go_SetDesiredTransformation(actor, slot, name, force)` and `go_EnableTransformationForSlot(actor, slot, enabled)`. The actor is the engine's saved handle (`index << 16 | serial`) pushed with `lua_pushlightuserdata`; `slot` is `"Attack"` or `"Defense"`. The engine resolves the power name locally and does the whole job: model, left arm, pose re-fit and the transform effect. It works on the puppet in both directions and needs no preload. The functions answer `true`/`false`.
- **Power names are `Alex<Power>`:** the description name hashes of the slots match `AlexClaws`, `AlexBlades`, `AlexHammerFist`, `AlexWhipFist`, `AlexMuscleMass`, `AlexShield` and `AlexArmor` (`hash("AlexWhipFist") = 5D87095518F5F848`). The slot descriptors use the same 64-bit `0x1003f` name hash, so the receiver matches the streamed hash against a local name list. `powersList`, `HUD_POWERS` and `HUD_TRANSFORM_SLOT` globals hold the catalogs (30 names in the 100 % save), but the stock names are enough.
- **Unequip needs an empty name:** `go_SetDesiredTransformation(actor, slot, "", false)` plus `go_EnableTransformationForSlot(actor, slot, false)` returns the actor to normal hands. Disabling the slot alone leaves the last model attached.
- **The desired-form call also publishes `HUDPlayerTransform`:** `GameDatabase::SetInt` (`0x107F8680`) is called with the `core::Name` at `0x1126CB90`, player 0, value = HUD power, index = slot, from the transformation handler at RVA `0x827D9`. The HUD quick-select node (`proto::FEHudPowerNodeQuick`, `0x104C5330`) reads that value and applies it to the local player, so a power applied to the puppet made the *local* player equip it; each side observed the change and sent it back, and both players cycled powers. The plugin detours `SetInt` and drops `HUDPlayerTransform` writes for 1.5 s around each puppet application; the player's own selections use callers `0x4C4F45`/`0x4C53B9` and pass through.
- **Lua C API (5.1) addresses used:** `lua_getfield` `0x1062CA40`, `lua_next` `0x1062D200`, `lua_type` `0x1062C370`, `lua_tolstring` `0x1062C610`, `lua_gettop` `0x1062C1B0`, `lua_settop` `0x1062C1C0`, `lua_pushlightuserdata` `0x1062C9C0`, `lua_pushstring` `0x1062C870`, `lua_pushboolean` `0x1062C9A0`, `lua_toboolean` `0x1062C5E0`; `engine::ProtectedCall` `0x107FFB10` (0 on success). `At()` takes RVAs (`address - 0x10000000`); passing the absolute address silently reads unrelated memory. Call only from the game thread (frame tick).
- **Transformation slots are per behaviour:** `+0xBC` (`transformationTemplate`) and `+0xD8` (`defaultLeftArmTemplate`) point to the same `content::MetaObjectTemplate` in the player and the puppet only because both wear the same form; the slot vectors (`+0x10..+0x14`) are separate. The old "shared template" reading was wrong; the local player changed because of the HUD publication above, not because the behaviours share state.

- **The whip cannot be worn by two actors in one process:** with the Lua path, the puppet can wear any power; but if it wears the whip and the local player later equips the whip, the engine builds the arm drawable from content that was already released. The first symptom was `PoseData::SetRestPose` writing through a zero base (`write at 0x4380`, the array offset of a failed 25,936-byte pose allocation); after allocating the pose on the system heap the same load faults in `pure3d::Shader::CopyConstants` (`read at 0x00000010`, a null shader) from `ExecuteRenderEvents` on the render thread. Holding the whip archetype/skeleton (`content::LoadObject::AddRef`) does not help, and reverting the puppet before the local equip does not either. Only the whip is affected (Claws/Blades/HammerFist/MuscleMass/Armour/Shield work in both directions). The plugin therefore skips the whip on the puppet by default (`whip_puppet=0`): the remote whip keeps the puppet's previous appearance but nothing crashes. `whip_puppet=1` re-enables the attempt for research.
- **Pose allocations use the thread's current heap:** `PoseData::PoseData(SkeletonData*, spaces)` calls `AllocateBoneData` → `core::HeapAlloc(core::GetCurrentHeap(), bytes)`. Content loading switches that heap temporarily; a pose of 90 joints with spaces=3 needs 25,936 bytes and a temporary render-thread heap returned null. A detour retried failed pose allocations on the system heap (`core::Free` finds the owning heap from the block), but it moved the crash to a null shader and could deadlock the render thread against the main thread's heap lock, so it was removed. The plugin restores the thread's heap around its own Lua calls instead.

- **The clone must stay out of the engine's animation jobs:** with the puppet's `choreo::Puppet` (`Attribute` vtable `0x10D9653C`) alive and its drivers cloned from the player, a few minutes of free roam end in a deadlock: the game thread waits forever in `core::EventWait` inside `choreo::RunPuppetJobs` (`0x10958F60`), and `puppet_static=1` (which clears the same attribute) runs for minutes without hanging. The pose stream is the only animator the puppet needs, so the attribute is cleared on spawn (`puppet_nochoreo=1`, default) and the drivers are not cloned. The avatar still animates, transforms and uses powers. The watchdog dumps the stalled thread's context and every process thread, which is how the wait was found.

The stream is gated by the distance between players (on below 150 m, off above 200 m); expired copies are moved to `y = -5000` and their slot is reused. Actors within `city_near` (60 m) of the **peer** are never sent: they already live in its world, which is what keeps the shared area free of double NPCs. - **City sync is positional and categorical:** the host streams `C2` (4 Hz, 32 entries) with a sender id, a category and a quantized position; the peer spawns **its own** actor of that category there. Categories come from the behaviour set: `AimBehaviour` -> soldier, `CharacterPedBehaviour` -> civilian, `CharacterMotionBehaviour` (without the other two) -> infected, `VehicleBehaviourAmbient` -> vehicle, any other `VehicleBehaviour`/`Tank` -> military vehicle. The representative template per category is learned from the peer's own loaded world (`LookupTemplate`, the object -> template index) and cached per category, with fallbacks (mutant -> infected -> civilian -> soldier; military vehicle -> vehicle). This avoids sending templates and avoids the tank-clone physics fault. Verified: 32 entries, soldiers and vehicles at the same places in both windows, no crashes in 3+ minute runs.

The city stream therefore keeps the keep-out filter and a small cap; a full union would need drawable-only copies instead of real game objects.

- **`core::Name(const char* text, int)` takes a second argument:** the constructor at `0x1005D5E0` is `__thiscall` and pops **two** stack arguments. - **The co-op state travels over SteamNetworkingMessages (`transport=steam`):** the same packets the loopback socket carries go through `ISteamNetworkingMessages` on channel 0, addressed with the peer's SteamID64 via `SteamNetworkingIdentity_SetSteamID64`; send flags `5` = unreliable + no Nagle + no delay, because a stale state packet is worth less than a dropped one. Received messages are drained in the frame tick and fed straight to `HandlePacket`, so the sync code does not know which transport delivered them. The peer is the other member of the lobby (`GetLobbyMemberByIndex`, skipping our own SteamID) and the host is the lobby owner, so the two players derive their roles from Steam and `role=` in `coop.ini` only matters for UDP. Sessions are accepted on `SteamNetworkingMessagesSessionRequest_t` (callback `1251`; the failure callback is `1252`, not the older P2P ids). `ISteamNetworkingMessage_t` only matters up to `m_cbSize`: the payload is at `+0`, the size at `+4` in both 4- and 8-byte packing, and the message is released through the flat `SteamAPI_SteamNetworkingMessage_t_Release`, so the struct layout differences between SDK packings never matter. `transport=udp` (the default) keeps the two-instance tests on the loopback socket and never initialises the socket in steam mode.
- **The XInput proxy is also the fallback ASI loader:** `xinput1_3.dll` is imported by `prototypeenginef.dll`, so it loads before the game starts even on a clean install. Its `DllMain` loads `prototype_fix.asi` then `prototype_coop.asi` from its own folder and calls each `InitializeASI` export, but skips any module Windows already has loaded so a second loader can never initialise a plugin twice. The launcher never writes `binkw32.dll`, `binkw32Hooked.dll` or `prototypeenginef.dll`; PrototypeFix's own binkw32 loader and files remain untouched. `prototype_coop.asi` is a standard ASI, so either PrototypeFix's loader or this proxy can load it, and the module check prevents double initialisation.
- **Packaging (`tools/package-coop.ps1`):** builds the plugin/proxy and the tabbed C# launcher, generates `menu.patch`/`lobby.patch` from the pristine movie, and stages `dist/PrototypeCoop.zip` with the launcher, `payload/mod` (plugin/proxy), patch data, credits and docs. PrototypeFix is not included; users install it separately from Nexus. The launcher installs the files, detects the user's PrototypeFix, fetches/verifies a compatible Steam API DLL, rebuilds `art/hud/protomainmenu.gfx` and `protodevmenu.gfx` from the user's own `art.rcf`, and removes a stale `steam_appid.txt`. No game assets, Valve DLL or executable patch are shipped.
## World sync: entity spawn chain (2026-11-20)

- **`engine::GameObjectSpawner::Create` is the central world-entity constructor:** `0x107F25C0` (RVA `0x7F25C0`), static `__cdecl` (plain `ret`, the caller pops `0x18` bytes), returns `engine::GameObject*` in EAX (`0` on failure). Symbol signature: `static GameObject* Create(content::MetaObjectTemplate* tmpl, const ObjectName& name, int heap, LoadInventory* inventory, LoadInventory* target, bool flag)`. Argument slots at entry: `[esp+4]` template (archetype), `[esp+8]` instance name, `[esp+0xC]` heap id, `[esp+0x10]` construction inventory (`0` = `gRootInventory`), `[esp+0x14]` destination inventory (`0` = `gGameObjects`), `[esp+0x18]` activation flag.
- **The archetype is the template pointer, not an integer:** `tmpl` is a `content::MetaObjectTemplate`; its factory decides the concrete class and `factory->type->Copy(...)` copies the template's property values into the instance. For replication send the template's name and resolve it with `LoadInventory::Find<MetaObjectTemplate>` (`0x10374650`); a raw pointer is not portable between processes.
- **What the body does:** it calls `tmpl->Create(heap, inventory ?: gRootInventory, name, flag)` through vtable slot `+0x24` (`content::MetaObjectTemplate::Create`, `0x10606A60`, `__thiscall`, `ret 0x10`); that allocates through `factory->Create()`, copies the template, and when `flag` is true calls `LoadObject::Slot3(inventory)` → `engine::GameObject::Slot3` (`0x107E0710`, `__thiscall`, `ret 4`), which registers the object and starts its behaviours. `Create` then adds the object to the destination inventory (`LoadInventory::Add`, `0x106032F0`) and, when `flag` is set, writes a handle into its `packageName` attribute.
- **`RegisterGameObject` is the single registration gate:** `0x107EEF00` (RVA `0x7EEF00`), `__cdecl`, one pointer argument, plain `ret`. It returns early when `object->index` (u16 at `+0x58`) is not `0xFFFF`; otherwise `gMasterTable->Allocate(object)` (`0x107E21D0`) returns the index (or `0xFFFF`) and stores it at `+0x58`. Its only direct caller is `GameObject::Slot3`; `MasterTable::Allocate` has only three callers, two of them the reserve-handle helpers.
- **Who calls the central create:** `0x107F25C0` has six direct callers (five systems plus the current-heap overload); the current-heap overload `0x107F2710` has 34 callers and the generated-name overload `0x107F2740` three. `GameObjectSpawner::Spawn` (`0x107F2390`) → virtual `CreateObject` (`0x107F27B0`, vtable slot 7) → `0x107F2710` → `0x107F25C0` is the actor-spawner path (`ActorSpawner::SpawnActor`, `0x906330`); `VehicleSpawner::Slot8` (`0x420DD0`, heap `0xAA`) and `PedestrianSpawner::Slot8` (`0x420EA0`, heap `0xA3`) call the six-argument form directly with `inventory = target = 0`, `flag = 1`.
- **Replicated vs organic spawns are tagged by the mod:** the engine has no network concept, so the client marks its own replicated spawns with a thread-local depth counter around the direct call and suppresses everything else at `RegisterGameObject` (or `GameObject::Slot3`): a skipped registration leaves `index = 0xFFFF`, no handle resolves and the world never sees the object, while the caller still gets a valid pointer (returning `0` from `Create` crashes callers that dereference the result). The object is still added to the destination inventory by name, so a fully inert suppression must also skip `LoadInventory::Add`.

### Ambient population, traffic and military spawns (2026-11-20)

- **`proto::AmbientManager` is the ambient director:** singleton `0x11267760`, 0x618 bytes, built by `AmbientManager::AmbientManager(const AmbientConfig*)` `0x1041FA40`; `AmbientManager::Shutdown` `0x1041D780` clears the singleton and tears the arrays down. The population knobs are `__thiscall` with one float and `ret 4`: `SetPedestrianDensityScale` `0x10409D70` writes `+0x280`, `SetVehicleDensityScale` `0x10409DB0` writes `+0x284`, `SetMaxCharacters` `0x10409D00` writes `config+0x5C`, `SetNearSpawnDistance` `0x10409D30` writes `config+0x40`, `SetFarSpawnDistance` `0x10409D10` writes `config+0x44`, `SetSpawnAreaSize` `0x10409D50` writes `config+0x38`; `SetMaxVehicles` `0x10409CF0` is empty. Zeroing the two density scales stops the manager from generating ambient spawn tasks.
- **The ambient spawners are content objects under the manager:** `VehicleSpawner` (vftable `0x10E023D4`, 9 slots) and `PedestrianSpawner` (vftable `0x10E02404`, 9 slots) derive from `AmbientSpawner` (vftable `0x10E02380`, slot 8 is pure). Their `Slot3` (`0x10420810` / `0x10420860`, `__thiscall`, `ret 4`) hand the spawner to the manager: `AddVehicleSpawner` `0x10409990` pushes into the block at `manager+0xE4`, `AddPedestrianSpawner` `0x104099B0` pushes into `manager+0x170` (`__thiscall`, one pointer, `ret 4`). `IsReady` (`0x10420830` / `0x10420880`) calls the empty `VehicleSpawnerReady`/`PedestrianSpawnerReady` hooks.
- **`Slot8` is the actual ambient spawn:** `VehicleSpawner::Slot8` `0x10420DD0` and `PedestrianSpawner::Slot8` `0x10420EA0` are `__thiscall` with one argument and `ret 4`. They call `engine::GameObjectSpawner::Create(templateName, uniqueName, 0xAA / 0xA3, 0, 0, true)` and send `CreateVehicleMessage(argument)` / `CreatePedMessage(argument, type)` to the new object; the pedestrian slot also writes the object's `packageName` attribute. The argument is the spawn task the new vehicle or pedestrian reads its position from.
- **The per-frame ambient task executor is `0x10424530`:** `__thiscall bool(Task* task, int, bool)` with `ret 0xC`. It takes a queued spawn task, calls `task->subject->vtable[8](task)` at `0x104245AA` (the spawner `Slot8` above), updates the task and queue counters (`task+0x2C/0x30`, queue `+0x68/+0x6C/+0x78`, ratio threshold `task+0x38`, countdown `task+0x40`) and pops the task (`task+0x28`). Its only callers are `0x10425260` and `0x10426D20` (both `__thiscall`, `ret 0x10`), which makes it the choke point for traffic and pedestrian spawning.
- **Military and hive reinforcements are fight-track actions, not a spawner class:** the game's AI branch items (`militarySpawner`, `hive`, `STRIKETEAM_AREA`, `EVENT_MILITARY_OPPORTUNITY`; `code/engine/statics/aifightitemnames.cpp`) drive `engine::SpawnObjectTrack` (`0x108B6480`) → `SpawnObjectAction` (`0x108F3F40`) → `SpawnObjectAction::Slot5` `0x108F3FD0` (`__thiscall bool(int, float)`, `ret 8`), and `fight::SpawnTrack` → `fight::SpawnAction::Slot5` `0x105B1BC0` (`__thiscall bool(int, float)`, `ret 8`). The tracks are executed by `fight::Sequencer::Update` `0x105A42F0` (`__thiscall void(int)`, `ret 4`), which is called from the animation, fight and vehicle systems.
- **Crowd and actor spawners spawn on activation, not per frame:** `engine::ActorSpawner::SpawnActor` `0x10906330` (`__thiscall`, hidden `GameObjectHandle*` result plus `LoadInventory*`, `ret 8`) and `engine::ActorCrowdSpawner::SpawnGrid` `0x10906450` (`__thiscall void(LoadInventory*)`, `ret 4`); `ActorCrowdSpawner::Slot3` calls `SpawnGrid` once when the object activates and the grid is created in one go.

### Suppressing organic spawning on the Client without leaks (2026-11-20)

- **Ambient only, zero allocation:** call `gAmbientManager->SetPedestrianDensityScale(0.0f)` (`0x10409D70`) and `SetVehicleDensityScale(0.0f)` (`0x10409DB0`), optionally with `SetNearSpawnDistance`/`SetFarSpawnDistance`/`SetMaxCharacters`. No ambient task is generated, so no `GameObject` is constructed and nothing has to be freed. Existing ambient entities stay; despawn them separately if the mirror replaces them.
- **Global gate, leak-free:** mark our own replicated spawns with a thread-local depth counter around the direct `GameObjectSpawner::Create` call and hook `engine::GameObject::Slot3` `0x107E0710` (`__thiscall`, `ret 4`): when the counter is zero and client suppression is on, skip the whole body (no `RegisterGameObject`, no `behaviours.Slot1`), so the object keeps `index = 0xFFFF` and no behaviour runs. Queue the object and, on the next frame, call `content::LoadInventory::Remove(gGameObjects, object, true)` `0x10603560` (`__thiscall bool(LoadObject*, bool)`, `ret 8`): `Add` (`0x106032F0`) took one reference through the object's `AddRef`, `Remove` releases it per registered name and the object deletes itself through its virtual destructor.
- **Do not return `0` from `GameObjectSpawner::Create`:** callers use the result immediately (`Slot8` sends the create message to it), so a null return crashes. Do not free it inline either: the same pointer is used after `Create` returns, hence the next-frame removal.
- **`RegisterGameObject` alone is not enough:** skipping only `0x107EEF00` still starts the behaviours and keeps the inventory's reference, which is exactly the leak this note is about; the `Slot3` skip plus `LoadInventory::Remove` is the complete pair.

### Client puppet AI: behaviour/AI tick and suppression (2026-11-20)

- **Behaviour scheduling:** a `GameObject` embeds its `engine::BehaviourController` at `+0x20`; the controller keeps the `Behaviour*` array at `+0x10` (begin) / `+0x14` (end), its owner at `+0x4`, the per-behaviour schedule at `+0x2C` (8-byte entries: accumulated time, pass/updated/scheduled/active flags, frame skip and phase) and the update mask at `+0x28`. Every `Behaviour` has its owner at `+0x4`, and its `Update(float, unsigned short)` is vtable slot 4 (`+0x10`).
- **Per-frame chain:** `engine::UpdateGameObjects(UpdateContext context, unsigned short mask)` `0x107F0410` is `__cdecl` (four stack dwords: the 12-byte context with `dt` at `+8`, plus the padded mask; plain `ret`) and walks the master table; for each active object it calls `BehaviourController::UpdateBehaviours(float dt, unsigned short mask)` `0x108398A0` (`__thiscall`, `ret 8`), which loops the behaviour array and calls each active behaviour's vtable slot 4 (`call [eax+0x10]`) unless the schedule says the behaviour is inactive or skipped this frame.
- **The AI brain is `proto::AiTreeBehaviour`:** `Update(float, unsigned short)` `0x103C8E50` (`__thiscall`, `ret 8`, vtable `0x10DFCADC` slot 4 through thunk `0x10009EEE`) runs the AI context: it time-slices with `+0x6D`/`+0x6E`/`+0x148`, calls `fight::Sequencer::Update` `0x105A42F0` (which executes the branch's movement, attack and spawn actions) and sends `ThreatClearMessage` to the owner. It derives from `engine::FightTreeBehaviour` (branch at `+0xC`, sequencer at `+0x18`, params at `+0x60`).
- **Disabling the behaviour is the clean AI-off switch:** `Behaviour::SetEnabled(bool)` `0x107EEB50` (`__thiscall`, `ret 4`; in code always `imageBase + 0x7EEB50`) sets the inactive flag and refreshes, which runs `OnActiveChanged(false)`; `AiTreeBehaviour::OnActiveChanged` `0x103C7980` resets its sequencer and calls `gAISystem->RemoveTargetable(owner)`, and the controller clears the schedule's active bit so `UpdateBehaviours` never calls it again. `BehaviourController::SetEnabledOfType(const type_info&, bool)` `0x10839FF0` (`__thiscall`, `ret 8`) does the same for every behaviour of a type; `SetEnabledAll(bool)` `0x10839F90` (`__thiscall`, `ret 4`) is too broad because it also disables the render, pose and physics behaviours.
- **What keeps running:** `proto::CharacterMotionBehaviour::Update` `0x10063B50` (drift/pushback and character motion), `engine::PoseAnimationBehaviour::Update` `0x10920B50`, `engine::MotionTreeBehaviour::Update` `0x1091F5B0` (the pose stream keeps playing the host animation), `engine::PhysicsBehaviour::Update` `0x109242C0` and the render behaviours are untouched, so the puppet keeps its mesh, collision and animation.
- **Resolving the owner:** `*(GameObject**)((char*)behaviour + 4)`; the controller's owner is also at `+4`. The object's master-table index is the `u16` at `+0x58` (`GetHandle` `0x107EEF60`).
- **Client policy:** after a replicated spawn (`g_NetSpawnDepth > 0`), walk the puppet's controller array and call `SetEnabled(false)` on every behaviour whose vtable is `RVA 0xDFCADC` (AiTreeBehaviour). Optionally keep a guard in `AiTreeBehaviour::Update` that returns when the owner is a puppet, for cases where a mission re-enables it. Hooking only the tick leaves the AI registered in `gAISystem` with its branch state alive; disabling the component is the cleaner and cheaper option.

### Client culling, distance LOD and despawn protection (2026-11-20)

- **The AI character budget is the distance LOD system:** `proto::gAISystem` `0x11263AB0`; its `soldierBudgets` member sits at `+0x10`. Each `CharacterBudgetEntry` is 0x50 bytes: `GameObjectHandle` at `+0`, `CharacterBudgetPolicy` at `+8` (class name, `despawnDistanceSquared` at `+0x10`, `freezeDistanceSquared` at `+0x14`, priority and weights), `distance` at `+0x30`, `levelOfDetail` at `+0x40`. `SoldierBudgets::Find(handle)` `0x10386540` (`__thiscall`, `ret 4`) returns the entry or the array end; `SetUnlimitedDistances(handle, true)` `0x103865A0` (`__thiscall`, `ret 8`) sets both distances to 1e12 for that entry; `SetDespawnDistanceSquared(handle, &value)` `0x103867D0` sets just the despawn radius.
- **The per-frame distance check:** `SoldierBudgets::UpdateDistances(float dt)` `0x10388DA0` (`__thiscall`, `ret 4`, `ecx` = SoldierBudgets) reads the player matrix, computes each entry's distance with `FUN_103873D0` (writes `entry+0x30`), stores the cell flag and calls `SoldierBudgets::UpdateEntryLOD(entry, dt)` `0x10388180` (`__thiscall`, `ret 4`, `ecx` = entry). `UpdateEntryLOD` compares `entry+0x30` with `policy+0x10` / `policy+0x14` and sets `levelOfDetail` (`+0x40`) to 4 normally, 0x14 beyond the despawn distance, or 8 beyond the freeze distance, sending the LOD, ragdoll and uninterruptible messages; it does **not** destroy the object.
- **Where deletion actually happens:** every automatic removal ends in `engine::DeferUpdate(GameObjectHandle handle, bool force)` `0x107EF710` (`__cdecl`, 4-byte handle + bool, plain `ret`), which queues the handle in `gDeferredObjects` unless `force` is false and the object is ready; `FlushDeferredUpdates()` `0x107EF7B0` (`__cdecl`, plain `ret`) then calls `object->IsReady()` (vtable slot 4 at `+0x10`) and `content::LoadInventory::Remove(object, true)` `0x10603560` (`__thiscall`, `ret 8`). 92 sites reach it through `GameObjectHandle::DeferUpdate` `0x107EE360` (`__thiscall`, `ret 4`, `ecx` = handle), including the budget's over-budget `ReturnSpawnedObjects` `0x10388F40` (only objects with a `spawner` attribute), the scenario `FinishDeactivation` `0x1048A320` and the actor/prop spawner cleanups. `proto::AmbientManager::RemoveVehicle` `0x104120F0` only unlinks the vehicle from its lists; it does not delete the GameObject.
- **Resolving the object from an entry or handle:** master table `gMasterTable` `0x1128348C`, 8-byte entries (object at `+0`, serial `u16` at `+4`, flags `u16` at `+6`): `index = handle & 0xFFFF`, `serial = handle >> 16`, `object = entries[index].object` when `entries[index].serial == serial`. From a `CharacterBudgetEntry` the handle is the first dword.
- **Client protection:** after a replicated spawn, resolve the handle and call `soldierBudgets->SetUnlimitedDistances(handle, true)`; if the entry does not exist yet, retry when it is added or rely on the veto below. Hook `engine::DeferUpdate` `0x107EF710` and skip it for any handle whose object is in the NetID puppet map unless the mod's `DESTROY_ENTITY(NetID)` handler is running (`g_allowPuppetDestroy` flag); the host's explicit destroy then calls `LoadInventory::Remove(object, true)` `0x10603560` and drops the NetID. This blocks budget, spawner, scenario and streaming cleanup uniformly while keeping explicit deletion.

## Co-op session gating (2026-11-21)

The online lobby and the replication loop are separate. A lobby can stay open
while the host returns to the main menu, so "peer connected" is not enough to
decide that a match is co-op.

The plugin now has an explicit session state:

- `CoopStartScript` (Online PLAY) and `CoopNewGameScript` (Online NEW) arm a
  pending session on the host.
- The guest arms it when it receives the host's `G2` (saves coming), `G3` (new
  game) or `G1` (start) packet.
- The session becomes active only after a local player object exists **and**
  the HUD is loaded.
- Leaving gameplay (no player/HUD for 3 s) clears the session and resets the
  puppet/remote state. The transport and Steam lobby can stay alive for the
  frontend, but `HandlePacket` ignores gameplay packets while no session is
  active and the send block is skipped.
- `CanSpawnPuppet` requires the active session, so main-menu Continue/New Game
  never creates a remote avatar.

This is what keeps a lobby opened earlier from turning a later main-menu
Continue/New Game into co-op. Online PLAY/NEW remains the only entry point.

## Launcher lobby presence (2026-11-21)

The launcher is built as x86 so it can load the same 32-bit Steam API DLL the
game uses. It initialises Steamworks in a short-lived process, using
`SteamAppId`/`SteamGameId` = `10150` (no `steam_appid.txt` is created), calls
`RequestLobbyList` with `game = prototype-coop`, and sums
`GetNumLobbyMembers` for each returned lobby before `SteamAPI_Shutdown`.

The count shown on the Play tab is therefore **players inside public co-op
lobbies**, not every installation and not solo players. It is the same lobby
set the SEARCH row uses. If Steam is closed or the mod is not installed yet,
the tab says so and the count is unavailable.

## Video options and graphics settings (2026-11-21)

The video screen is Scaleform GFx, not native code, and it is data-driven. The
relevant entries in `art.rcf` for the 2025 build are:

| RCF hash | Size | Contents |
|---|---:|---|
| `3A588791` | 34,329 | `protovideooption.gfx`, the video settings screen |
| `BFE10927` | 2,692 | `protooptionsoverlay.swf`, the shared option toggles/sliders |
| `80FFFD7F` | 9,414 | `protooptions.gfx`, the Video/Audio/Controller hub |
| `01BBF7EE` | 72,592 | options manifest/screen-name table |

The video movie creates its rows from `mVideoOptions` in `InitializeOptions`
(and `VideoOptionSelection`) and binds them to these six persisted settings:

- `SettingVideoResolution`
- `SettingVideoAALevel`
- `SettingVideoVSyncEnabled`
- `SettingVideoShadowDetail`
- `SettingVideoGraphicQuality`
- `SettingVideoGammaCorrection` (the gamma slider)

Those are the only video values the game stores; the screenshot's five rows are
the visible subset. The value order is `0..2` for AA (4x, 2x, off), V-Sync
(on, off), shadow detail (high, medium, low) and graphic quality (high, medium,
low); gamma is `1..5`.

`SettingVideoResolution` is an index into the 17-entry table returned by
`rm_GetNumAvailableResolutions`. On the test machine index 0 was the current
desktop mode (1920x1080), followed by 800x480, 800x600, 1024x768, 1152x720,
1152x864, 1280x720, 1280x800, 1280x1024, 1440x900, 1600x1200, 1680x1050,
1920x1080, 1920x1200, 2048x1152, 2048x1536 and 2560x1600. Index 0 is the safe
choice for "desktop"; explicit modes are matched by width/height.

The plugin reads `video_override`, `video_resolution`, `video_aa`,
`video_vsync`, `video_shadow`, `video_quality`, `video_gamma` and `video_lod`
from `coop.ini`, then calls `engine::GameDatabase::SetInt` with the same subject
names the video screen uses. The renderer observes those subjects, so this
applies the values without patching `protovideooption.gfx`. The launcher's
**Game settings** tab writes those keys; the in-game menus are untouched.

The global geometry LOD bias is `rm_SetGeoLODBias` (`0x102E0070`), which writes
the float at `0x11075120`. The game's Graphics quality sets it to 1.5/1.0/0.5
for high/medium/low; the plugin applies `video_lod` after the quality value so
an explicit bias wins at startup. Larger values keep geometry detail farther
away. This is the closest global "render distance" control; actual object
streaming is cell-based, so there is no single draw-distance scalar.

PrototypeFix already exposes the safe, supported graphics controls through its
own `prototype_fix.ini`: FOV offset, shadow-map resolution, custom/window
resolution, borderless window, FPS cap, tick-rate limit, VRAM amount, DInput
filtering and the crash fixes. The launcher's **Game settings** tab edits those
keys too and leaves the GFx movies and PrototypeFix binary untouched.

The render manager exposes many more `rm_*` functions (`rm_SetShadowResolution`,
`rm_SetGeoLODBias`, `rm_SetGlobalShadowRangeHack`,
`rm_EnableParticleSystemThrottle`, `rm_ToggleDistortion`,
`rm_SetColourMatrixGrain`, `rm_SetFillRateCapNIS`, etc.), but they are runtime or
developer toggles, not saved settings. Calling them from the menu would require
a plugin bridge and per-setting testing. If more settings are added later, the
practical path is a separate `graphics.ini` read by this plugin, with each
`rm_*` call enabled only after it has been tested in both host and guest;
patching extra rows into `protovideooption.gfx` is possible with the same GFx
patch approach, but the row still needs a real backing variable.
